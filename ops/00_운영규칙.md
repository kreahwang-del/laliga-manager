## 2. 시작 절차(새 대화 / 작업 공간 초기화 후)
1. Project 문서 `claude/WSM_운영규칙.md`와 `claude/WSM_진행현황.md`를 읽는다.
2. `git clone` 후 `dev` 브랜치로 체크아웃한다. clone이 안 되면 작업 공간에 저장소를 추가한다.
3. `ops/01_진행현황.md`의 '다음 할 일'을 확인하고, 사용자에게 한 줄로 이어서 할 일을 알린다.
4. 필요한 역할 지시문(`ops/roles/*.md`)을 읽고, 에이전트를 띄울 때 지시문 전문과 구체 과제를 함께 넘긴다.

## 3. 작업 단위 마무리 규칙(반드시)
- 의미 있는 작업 한 단위가 끝날 때마다 다음 세 가지를 한다.
  1. `dev`에 커밋한다(사용자가 브랜치 운영에 동의함). 메시지에 무엇을 왜 바꿨는지 쓴다.
  2. `ops/01_진행현황.md`를 갱신한다: 완료, 다음 할 일, 막힌 점, 검증 수치.
  3. 사용자 결정이 있었으면 `ops/02_결정기록.md`에 날짜와 함께 추가한다.
- 하루 작업이 끝나거나 큰 단계가 끝나면 Project 문서의 `WSM_진행현황.md`도 갱신한다. 자주 바꾸지 않는다.
- 2시간 넘는 시뮬레이션은 나눠 돌리고, 중간 결과(jsonl)도 커밋한다.

## 4. 에이전트 운영
- Claude(총괄)가 과제를 쪼개고 역할 에이전트를 띄워 맡긴다. 결과는 총괄이 검증한 뒤 반영한다.
- 역할: 엔진·시뮬 / QA(밸런스·검증) / 가명화·권리 / 디자인(UX·UI) / 플레이테스트. 지시문은 `ops/roles/`.
- 만드는 쪽과 판정하는 쪽을 나눈다.
  - 엔진·밸런스 변경: QA가 합격 기준을 먼저 정한다 → 엔진·시뮬 구현 → QA 독립 검증 → 총괄 판정.
  - 화면·문구만 바꾸는 변경은 QA 수치 검증을 생략하고 플레이테스트 확인으로 갈음한다.
  - QA = 숫자(밸런스·회귀·공략법), 플레이테스트 = 화면 조작(결함·불편·사용성).
  - 같은 파일을 동시에 고치지 않도록 QA는 구현이 끝난 뒤 투입한다.
- 서로 독립적인 작업만 동시에 맡긴다. 같은 파일을 동시에 고치지 않는다.
- 웹 검색 한도는 한 번에 띄운 에이전트들이 함께 쓴다(약 200회). 동시 에이전트는 2~3개로 제한한다.
- 에이전트는 사용자 승인 없이 커밋·배포하지 않는다. 총괄이 검증 후 커밋한다.

## 5-1. 소스 작업 방법(2026-10-29부터)
- 원본은 `src/`다. `work/cur.html`은 빌드 결과물이며 직접 고치지 않는다.
- 빌드
  - 개발본: `python src/build.py` → `src/dist/cur.html`
  - 배포본: `python src/build.py --deploy --appv <v>` → `src/dist/index.html`
- 엔진은 `src/engine/` 한 곳만 고친다. 화면 엔진과 워커용 ENGINE_SRC는 빌드가 함께 만든다.
- 앱 코드는 `src/app/`의 구역별 파일이고, 결합 순서는 `src/app/order.txt`다. 데이터는 `src/data/`(선수 1명 = 1줄 JSON)다.
- 수정 뒤에는 반드시 확인한다.
  - 빌드가 성공하는지
  - 같은 시드의 AI끼리 경기 해시가 그대로인지(엔진을 고쳤으면 의도한 변화만 있는지)

## 6. 배포 루틴(main)
1. `python src/build.py --deploy --appv <v>`로 `index.html`을 만든다(`LGMKT_OFF=false`, `APPV=<v>`가 자동 적용).
2. `version.json`을 갱신한다.
3. `main`에 커밋하고 push한다(사용자 승인 후).
4. Artifact(https://claude.ai/artifact/4gVvBo1wz9W1zDRew1pTiy)를 같은 주소로 다시 게시한다.
5. 설계 문서에 버전 기록을 추가한다.
